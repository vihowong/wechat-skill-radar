# 好读：让不懂这行的人也读得下去

这份文件管"简单易懂"和"读下去"。去 AI 腔的硬约束见 `writing-craft.md`，结构与平行字段见 `editorial-rules.md`。

## 一、先接受读者的三个默认状态

1. **他不认识你写的项目，也不懂那些术语。** 你觉得是常识的东西，对他来说是新词。
2. **他是滑着看的。** 先扫小标题、加粗、图片、数字，决定要不要停下来读。
3. **他只关心"这跟我有什么关系"。** 功能列表对他没有意义，能省他多少时间才有意义。

由此推出两条铁律：**每节开头先给结论**，**术语第一次出现就给一句解释**。

## 二、讲人话的五条

| 做法 | 反例 | 改法 |
| --- | --- | --- |
| 术语先翻译再用 | 「基于 ReAct 范式的 Agent 编排框架」 | 「它能让模型边想边调工具——你可以理解成一个会自己找工具的助手」 |
| 一句一个意思 | 一句话里塞三个并列从句 | 超过 40 字就拆；一段只讲一件事 |
| 给参照系 | 「耗时 41 分钟」 | 「41 分钟，比我自己整理这份材料少一半时间」 |
| 外文名先中文后原词 | 通篇 RAG、MCP、LoRA | 第一次写「检索增强（RAG）」，之后再用缩写 |
| 动词优先 | 「进行配置」「实现效率提升」 | 「配一下」「快了三倍」 |

补充三条细则：

- **缩写第一次出现必须展开**，否则读者会直接跳过整段。
- **数字要给量级感**：「3.2 万亿 token」后面补一句「相当于每天被调用几十万次」这类可比的说法；拿不准就不写这个补充。
- **不做无解释的对比**：「比同类快」要写清快在哪里、在什么条件下。

## 三、让人读下去的结构

1. **前 100 字**回答三件事：写给谁看、读完能拿到什么、大概几分钟。不要用行业大势开场。
2. **小标题写成结论或读者的问题**，不要写成名词短语：
   - 差：「功能介绍」→ 好：「装完第一步先干什么」
   - 差：「性能表现」→ 好：「它到底快不快，官方数据怎么说」
3. **每节第一句给结论或场景**，后面才是展开和证据。
4. **每 2–3 段给一个可核对的东西**：数字、命令、截图、官方原话、出处链接。
5. **桥句直说下一节讲什么**，不要用"后面会讲到"这种悬念——读者会直接退出。
6. **人称**：用"你"称呼读者；"我"只用来表示"我查了 / 我看了 / 我认为"，不用来伪造体验。
7. **结尾给行动**：先做什么、去哪看文档、什么情况别用。

## 四、四种框架各自的"好读"重点

| 框架 | 读者最想知道 | 所以先写什么 | 千万别写成 |
| --- | --- | --- | --- |
| 项目手册 | 它是什么、我怎么用起来 | 一句话定位 + 第一条命令 | 官方 README 的翻译版 |
| 科普解读 | 这跟我有什么关系 | 它解决的问题 + 一个生活化类比 | 术语与发展史 |
| 清单合集 | 我该先装哪个 | 按用途分组 + 每个一句"替你做什么" | 十个项目的功能罗列 |
| 选型指南 | 这几个怎么选、我的情况选谁 | 一张对比表 + 三种典型场景的建议 | 参数堆砌，最后不给结论 |

## 五、劝退清单（写完扫一遍）

- 连续三段都是功能罗列，没有一句场景。
- 术语第一次出现没有解释，或者一段里出现三个以上未解释的英文词。
- 数字没有参照系，读者不知道这是好还是差。
- 通篇没有一张图、一张表或一条命令。
- 每节开头都是同一个句式（例如都以"XX 是一个……"起头）。
- 只有官方口径的复述，没有一句"对读者意味着什么"。
- 小标题连起来读，像目录而不像要点。
- 结尾没有告诉读者下一步做什么。
- 通篇没有一条可以照抄的命令、步骤或对照表——读者读完不知道能干什么。
- 说了"可以配置"却没给具体位置和步骤。

前四条在 `qa-checklist.md` 的目视项里要逐条过；机器能查的（段落长度、句式重复、标点频次、信息密度）由 `qa.py` 拦。
