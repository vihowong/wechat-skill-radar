# 选题：四种框架，多个来源

这份文件管「这一期写什么、写成哪一种」。抓取命令与来源清单见 `sources.md`，文章骨架见 `editorial-rules.md`。

## 一、先定框架（每期只选一种）

文章的基本框架围绕四件事：**实用、知识普及、项目手册、指南**。选一种，不要混着写。

| 框架 | 什么时候用 | 篇内数量 | 主要素材 | 读者拿到什么 |
| --- | --- | --- | --- | --- |
| **项目手册** | 一个项目 / 模型 / 功能值得讲透 | 1 个主角（可带 1–2 个对照） | 官方文档 + README + issue 区 + 官方公布的数字 | 一套能照着跑起来的步骤与注意事项 |
| **科普解读** | 一个技术方向、一个事件需要讲清楚 | 1 个主题（可举 4–8 个项目当例子） | 抓取清单 + 官方材料 + 社区讨论 | 看懂这件事，以及它跟自己的关系 |
| **清单合集** | 读者是某一类人，需要一组能直接装的技能 | 8–10 个 | 抓取清单 + 各仓库 README | 先装哪个、怎么装、装完干什么 |
| **选型指南** | 同类项目一下子冒出好几个，读者在纠结选谁 | 3–6 个同类对比 | 官方参数 + 许可证 + 活跃度 + 社区口碑 | 一张对比表 + 三种典型场景的结论 |

判定标准两条：

1. 读者扫一眼标题和封面，能说出**这篇讲什么、给谁看**。
2. 你自己能说出**这篇是哪一种框架**（手册 / 科普 / 清单 / 指南）。说不出，说明框架没定住，写起来一定散。

框架要写进项目文件夹名和稿件元信息（例：`2026-10-10_项目手册_MCP上手`、`2026-10-14_选型指南_办公Agent三选一`）。

**每种框架卖的是一种确定的东西**：

- 项目手册卖的是**可照做的步骤**——从零到跑通第一步，一条一条写清楚。
- 科普解读卖的是**理解**——这件事为什么发生、和以前有什么不一样、对普通人意味着什么。
- 清单合集卖的是**省事**——一篇读完知道先装哪个。
- 选型指南卖的是**决定**——读者看完能当场选一个，不用再翻十个页面。

## 二、主题口径：AI / 科技这条线上的一件事

主题可以是：

- 一个具体项目、模型、产品或开源库；
- 一个技术方向：Agent、MCP、RAG、语音、视频生成、端侧推理、评测……；
- 一类人的需求：做短视频的、做研究的、做跨境电商的、写周报的；
- 一个事件或现象：某榜单变化、某次发布、某个项目突然火了。

两条边界：

1. **不脱离人工智能与科技。** 选题、举例、配图元素都在这条线上。
2. **一篇只有一个主角群。** 可以横跨行业，但不要把两个不相干的主题塞进一篇；真要一起写，得有一条能说清的关系（比如"同一类活，两种做法"）。

相邻两期不要重复同一个主题或同一个主角。间隔几期之后再写可以，但必须带新的数据或新的进展（版本更新、榜单变化、新出的文档）。

## 三、来源与热度判断

来源清单、抓取命令、各平台的可用姿势都在 `sources.md`（GitHub、Hacker News、Reddit、X、网页搜索）。
判断"够不够热"至少凑够两条线，不要只凭一个来源下结论：

| 信号 | 怎么看 |
| --- | --- |
| GitHub | 星标量级 + 近两周星标增速 + 是否仍在更新（`pushed_at`） |
| Hacker News | 分数与评论数；评论里在争什么比分数更有信息 |
| Reddit | 单帖热度；多个子版在同一周提到同一件事更可信 |
| X | 转发与引用讨论，注意区分作者自荐与真实使用 |
| 官方 | 官方发布说明、文档更新日志、定价与额度页 |
| 榜单 | LMArena、Artificial Analysis、OpenRouter 等，必须标抓取日期 |

## 四、入选与淘汰（清单与指南形态）

按顺序过筛，不符合的直接换下一个：

1. **与本期主题相关**：项目名、描述或 README 能看出它属于这个方向。
2. **实用价值高**：读者照做能在一件真实、反复发生的活上省时间。只能做演示、交不出东西的，降级或不用。
3. **上手简单**：优先「一条命令装完」（●○○），其次「装完选一次配置」（●●○）。要装环境或配密钥的（●●●）一期最多 2–3 个，并且要写明缺什么。
4. **近期仍活跃**：`pushed_at` 在 45 天内；项目手册可以放宽，但要写明它多久没更新了。
5. **未收录过**：跟同一条内容线已发的文章去重（见第五节 `_已做主题.md`）。
6. **资料够写**：官方文档、README、参数、限制、安装命令都查得到。**只有一个三行 README、issue 区没人说话的，写不成手册，最多在清单里占一行。**
7. **授权看得懂**：许可证是 MIT / Apache-2.0 / BSD 这类放心引用；GPL 只做介绍；没有 LICENSE 或 CC BY-NC 的，只做点评、不复制内容（见 `compliance.md`）。

## 五、去重与轮换

在内容线根目录维护一份 `_已做主题.md`，一行一期：

```
2026-10-10 | 项目手册 | MCP 从装到跑通 | owner/repo-a
2026-10-14 | 清单合集 | 给做视频的人的 8 个技能 | owner/repo-b, owner/repo-c, …
```

没有这份文件时，用历史项目文件夹名加各期的 `_工作文件/` 兜底。

同一个项目不重复收录，哪怕星标又涨了；真需要再提，只能在结尾一句话带过。

## 六、资料凑不够怎么办

- **清单形态：4–6 个就能出。** 结尾写清"这个方向刚起步，现在是入场时间"，把数量少当成信息，而不是缺陷。
- **少于 4 个就换框架。** 改成科普解读（用抓取分布当内容：哪类关键词只搜到个位数项目、最高星标多少），或者改成项目手册（挑资料最全的那一个写透）。
- **选题够热但资料很薄**（只有一条发布公告、没有文档）：写成科普解读里的一个例子，不要硬撑成手册。
- **永远不要跨主题凑数**，也不要拿非项目类内容（纯清单、数据集、课程）充数——读者看得出。
