# 编辑规则

## 一、内容边界

- 主题只有一个方向：**人工智能 / Agent Skill / 科技**。选题、举例、配图元素都不能脱离这条线。
- 数据来源是 GitHub 上的开源技能仓库。星标、更新时间、项目数量必须来自当期真实抓取，不沿用上一期的数字。
- 安装命令、仓库名、功能描述照抄对应 README，不发明、不臆测、不"顺手优化"命令。

## 二、结构

- **不要套用上一期的编辑模式。** 章节怎么分、开篇怎么写、要不要放"本文要点"、图注什么语气，都按当期内容自己决定。可用的组织方式包括：按使用场景分、按上手难度分、按行业分、按工作流先后分、按"解决什么问题"分、按时间来分。
- 每期结构要让人一眼看出是"为这批技能设计的"，而不是把上一期的骨架填上新名字。
- **唯一必须保持一致的是篇内的平行字段。** 同一篇里逐个技能的说明要用同一套字段、同一顺序，例如：
  - 「它替你做什么 / 装它 / 什么时候最值」+ 一个上手门槛
  - 「解决什么 / 怎么装 / 怎么用 / 适合谁」
  - 「卡在哪 / 它怎么解 / 装它 / 谁该先装」
  字段名和顺序一旦定下，全期不改。
- 结尾固定：正文结语 → 免责声明 → 平台引导。**不加往期推荐，不加公众号名片。**

## 三、写作口径

- 面向"会用的人少、但用得深"的读者时，先讲它解决什么重复劳动，再讲怎么装；不要一上来堆功能清单。
- 少用形容词，多给可核对的细节：星标、项目数、作者自己的实测数字、安装命令。
- 每个技能最多三到四段，段落短（建议 ≤110 字），方便手机阅读。
- 涉及钱、健康、法务、投资等敏感场景时，写清边界与免责，不给结论性建议。
- 门槛分级（可直接沿用）：**●○○** 一句话装完；**●●○** 需要挑配置或准备材料；**●●●** 要装环境或配密钥。

## 四、抓取结论怎么写

抓取本身会产生"哪里有人做、哪里没人做"的分布，这类信息比单纯推荐更有价值：

- 可以在结语或单独一节里给出空白方向（例如某类关键词只搜到个位数项目、最高星标很低），但**不要编造原因**，可以说"规则按国家走、责任重，愿意公开分享的人少"这类有依据的推断，并标明这是抓取结果。
- 给出"这对读者意味着什么"的一句话，例如"给助手用的技能已经卷起来了，日常办公那几类还空着"。

## 五、数据口径

- 稿件末尾或元信息里写明抓取日期与来源（GitHub 公开页面 + 各仓库 README）。
- 星标数、项目数、更新时间都是快照值，发布前建议回仓库核对一次。
- 提醒读者：第三方技能是别人写好的指令，装之前先看内容、权限与数据三件事。
