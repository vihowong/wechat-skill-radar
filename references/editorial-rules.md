# 编辑规则

## 一、内容边界

- 主题只有一条线：**人工智能 / 科技**。选题、举例、配图元素都要落在这条线上。
- 四种框架选一种：项目手册、科普解读、清单合集、选型指南；框架写进文件夹名与元信息。
- **以真实信息为准，不需要本机实测。** 所有事实来自公开可核验的来源：官方页面、README、官方文档、issue 与讨论区、榜单。查不到的就不写。
- 项目名、星标、安装命令、参数、限制照抄原文，不发明、不臆测、不顺手"优化"命令。
- 版权、违规词、敏感话题、AI 生成标识，全部按 `compliance.md` 执行；碰红线就换选题。

## 二、选题：四种框架

- 来源、热度判断、入选标准、去重轮换，见 `topic-selection.md`；五个来源各自的抓取与可信度分级，见 `sources.md`。
- 不限定行业：主题可以是一个项目、一个技术方向、一类人的需求或一个事件，但**一篇只能有一个主角群**。
- 判定：读者扫一眼标题和封面，能说出这篇讲什么、给谁看；你自己能说出这篇属于四种框架里的哪一种。

## 三、结构：四种框架的骨架

下面是起点，不是模板；每期要能看出是为这批内容设计的，而不是上一期的骨架换名字。**篇内唯一必须一致的是平行字段**：同一篇里逐个项目的说明用同一套字段、同一顺序。

### 项目手册（1800–3500 字）

1. 开场三句：它是什么、谁需要它、读完能拿到什么（一套能跑起来的步骤）。
2. 它是什么：一句话定位 + 官方原话或官方数据（标日期与出处）。
3. 装它：照抄官方命令，写清前提（Node / Python / 密钥 / 平台账号）。
4. 跑通第一步：照抄官方的最小示例，说清输入什么、得到什么。
5. 常用操作：3–5 条最常用的命令或用法，每条配一句"什么时候用"。
6. 坑与限制：官方写明的限制 + issue 区反复出现的报错，写清各自来源。
7. 谁该用 / 什么人不用装（带上手门槛分级）。
8. 结语：先做哪一步。

必答五项：**它是什么、解决什么问题、怎么装怎么用、已知限制与坑（带来源）、适合谁**。缺一项就不算手册。

### 科普解读（1500–3000 字）

1. 一句结论开场：现在发生了什么（带日期与来源）。
2. 它解决什么问题：先给一个生活化类比，再上正式说法。
3. 和过去的做法差在哪：一段对照，或用一张小表。
4. 现在到哪一步了：谁在做、做到什么程度（引用抓取分布与官方数字）。
5. 坑与争议：社区在吵什么，两边的说法都写。
6. 对普通人意味着什么：一段话讲清跟读者的关系。
7. 结语：想上手的人现在可以做什么。

必答：**一个类比、一处限制或争议、一句"这跟我有什么关系"**。

### 清单合集（2000–3500 字）

1. 导语说清：写给谁、读完能拿到什么、怎么用这份清单（别一次全装，先挑最烦的那件活）。
2. 按用途分 3–5 组，每组先给一句"这组解决什么"。
3. 每个项目用统一字段（含上手门槛分级与安装命令），至少给一个读者能对号入座的场景。
4. 结语：先装哪个 + 一句边界提醒。

### 选型指南（1500–2500 字）

1. 一句结论开场：先说"如果你只想省事，先看 X"这类可执行的结论。
2. 一张对比表，维度固定：它是什么 / 上手门槛 / 价格或额度 / 许可证 / 最近更新 / 最适合的活。
3. 按三种典型场景给建议，例如任务急、要求稳、预算紧。
4. 每个候选三到四段：定位 + 官方数据 + **什么时候别选它**。
5. 结语：一句话结论 + 去哪看官方文档。

必答：**一张表、三种场景、每个候选的"什么时候别选它"**。

### 平行字段（选一组，全期不改）

- 「它替你做什么 / 装它 / 什么时候最值」+ 上手门槛
- 「解决什么 / 怎么装 / 怎么用 / 适合谁」
- 「卡在哪 / 官方怎么写 / 装它 / 谁该先装」

字段名和顺序定下之后，全期不改；连续性一旦破掉，读者就没法横向比较。

## 四、写作口径

- **真实优先。** 每句话都要能指回一个来源；官方口径、社区反馈、我的判断三档分开写（见 `writing-craft.md` 第一节）。不写没做过的第一人称实测。
- **简单易懂。** 术语第一次出现就解释、每节开头先给结论、数字给参照系、小标题写成结论或问题——细则与劝退清单见 `readability.md`。
- **能落地。** 每篇至少给一个读者能立刻用上的东西（可照抄的命令 / 最小示例 / 对照表 / 决策规则），并写清前置条件、预期结果、卡住时的下一步——做法与"落地四问"见 `writing-craft.md` 第四节。
- **少用形容词，多给可核对的细节**：官方原话、参数、命令、日期、榜单排名。
- 每个项目最多三到四段，段落短（建议 ≤110 字）；长短句交替，连续三段字数接近就拆一段（`qa.py` 会拦）。
- **去 AI 腔是硬要求**：禁用词、句式黑名单、标点频次，全部按 `writing-craft.md` 执行。
- 每个项目至少给一个读者能对号入座的使用场景（谁、在什么情况下用到它）。
- 限制与坑单独成节或单独成段，不要夹在夸奖里。
- 涉及钱、健康、法务、投资等敏感场景时，写清边界与免责，不给结论性建议（口径见 `compliance.md`）。
- 上手门槛分级沿用：**●○○** 一条命令装完；**●●○** 需要挑配置或准备材料；**●●●** 要装环境或配密钥。

## 五、标题：每期给一组候选

- 每期在发布稿元信息里给 **6–8 条标题候选**（1 条推荐 + 3–5 条备选），覆盖**至少 4 种钩子类型**；推荐标题 ≤20 个汉字，数字与正文一致。
- 不写标题党词，不写极限词（最强、第一、唯一、100%），不承诺结果，不拿第三方账号名当卖点；口径见 `titles.md` 与 `compliance.md`。
- 标题说清"给谁看"或"能拿到什么"，封面主标题说另一件事，两处不要写同一句话。

## 六、分布信息怎么写

抓取本身会产生"哪里有人做、哪里没人做"的分布，这比单纯推荐更有价值：

- 可以在结语或单独一节给出空白方向，例如某类关键词只搜到个位数项目、最高星标很低；**不要编造原因**，可以说"规则按国家走、责任重，愿意公开分享的人少"这类有依据的推断，并标明这是抓取结果。
- 给出"这对读者意味着什么"的一句话，例如"给编码助手用的技能已经卷起来了，日常办公那几类还空着"。

## 七、数据与出处口径

- 稿件末尾或元信息里写明抓取日期与来源（公开页面、各仓库 README、官方文档、榜单）。
- 星标、调用量、排名、价格都是快照值；发布前建议回原始页面核对一次。
- **正文里每个数字、命令、参数，都要能在 `素材/资料与出处.md` 里找到出处**（写：内容 + 来源链接 + 日期）。
- 官方口径与社区说法分开标：官方数据写"官方公布"，社区说法写"有人在 issue / 讨论区提到"。
- 提醒读者：第三方技能是别人写好的指令，装之前先看内容、权限与数据三件事。
