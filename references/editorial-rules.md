# 编辑规则

## 一、内容边界

- 主题只有一条线：**人工智能 / 科技**。选题、举例、配图元素都要落在这条线上。
- 三种形态都允许：单项目深挖、主题盘点、清单合集。每期只选一种，形态写进文件夹名与元信息。
- 数据来源只有两类：**公开页面**（仓库、官方文档、榜单）与**自己的实测**。两类不许混着写，来源与实测要分开标。
- 安装命令、项目名、功能描述照抄对应 README 或官方页面，不发明、不臆测、不顺手"优化"命令。
- 版权、违规词、敏感话题、AI 生成标识，全部按 `compliance.md` 执行；碰红线就换选题。

## 二、选题：三种形态

- 选题的来源、热度判断、入选标准、去重轮换，见 `topic-selection.md`；五个来源各自的抓取与可信度分级，见 `sources.md`。
- 不再限定"一期一个行业"：主题可以是一个项目、一个技术方向、一类人的需求或一个事件，但**一篇只能有一个主角群**。
- 判定标准：读者扫一眼标题和封面，能说出这篇讲什么、给谁看。

## 三、结构：三种形态的骨架

下面的骨架是起点，不是模板；每期要能看出是为这批内容设计的，而不是上一期的骨架换名字。**篇内唯一必须一致的是平行字段**：同一篇里逐个项目的说明用同一套字段、同一顺序。

### 单项目深挖（2500–4500 字）

1. 开头两句交代契机：我为什么现在写它（在测什么、被什么卡住、榜单上发生了什么）。
2. 它是什么：一句话定位 + 官方数据（标日期与来源）。
3. 我的测试设计：材料、任务、对照对象、怎么判分。这一节决定读者信不信后面的结论。
4. 按维度分节报结果，每节先给结论或场景，再给数字，再给截图。
5. 专门一节写它做不到什么，以及对照对象哪里做得更好。
6. 谁该用、怎么上手（一条命令），以及什么人不用装。
7. 结语：什么场景选它、什么场景别选。

必答项：测试设计、对照对象、耗时或成本、失败点。缺任何一项，就不是深挖，是转述。

### 主题盘点（1800–3000 字）

1. 一句结论开场：这个方向现在什么情况（谁在卷、谁还空着）。
2. 分成 2–4 组，每组一句"这组解决什么"，再进项目条目。
3. 每个项目用统一字段，并至少给一个读者能对号入座的场景。
4. 收口时给抓取分布：哪一类关键词只搜到个位数项目、最高星标多少，这对读者意味着什么。
5. 结尾点名先看哪个。

### 清单合集（2000–3500 字）

1. 导语说清：写给谁、读完能拿到什么、怎么用这份清单（别一次全装，先挑最烦的那件活）。
2. 按使用场景或上手难度分 3–5 节，每节先给一句"这节看什么"。
3. 每个项目用统一字段（含上手门槛分级与安装命令）。
4. 结语：先装哪个 + 一句边界提醒。

### 平行字段（选一组，全期不改）

- 「它替你做什么 / 装它 / 什么时候最值」+ 上手门槛
- 「解决什么 / 怎么装 / 怎么用 / 适合谁」
- 「卡在哪 / 它怎么解 / 实测结果 / 装它 / 谁该先装」

字段名和顺序定下之后，全期不改；连续性一旦破掉，读者就没法横向比较。

## 四、写作口径

- **实测优先。** 每篇至少三处"我做过"的证据（装了、跑了、数了、花了多少），写法见 `writing-craft.md` 第二节。
- **实测、转述、判断三种语气分开。** 转述要写"README 里写""作者称"；判断用"我觉得""如果你的活是……"引出。
- **少用形容词，多给可核对的细节**：星标、耗时、成本、命令、作者原话。
- 每个项目最多三到四段，段落短（建议 ≤110 字）；长短句交替，连续三段字数接近就拆一段（`qa.py` 会拦）。
- **去 AI 腔是硬要求**：禁用词、句式黑名单、标点频次、人味做法，全部按 `writing-craft.md` 执行。
- 每个项目至少给一个读者能对号入座的使用场景（谁、在什么情况下用到它）。
- 失败点与限制单独成节或单独成段，不要夹在夸奖里。
- 涉及钱、健康、法务、投资等敏感场景时，写清边界与免责，不给结论性建议（口径见 `compliance.md`）。
- 上手门槛分级沿用：**●○○** 一条命令装完；**●●○** 需要挑配置或准备材料；**●●●** 要装环境或配密钥。

## 五、标题：每期给一组候选

- 每期在发布稿元信息里给 **6–8 条标题候选**（1 条推荐 + 3–5 条备选），覆盖**至少 4 种钩子类型**；推荐标题 ≤20 个汉字，数字与正文一致。
- 不写标题党词，不写极限词（最强、第一、唯一、100%），不承诺结果，不拿第三方账号名当卖点；口径见 `titles.md` 与 `compliance.md`。
- 标题说清"给谁看"或"能拿到什么"，封面主标题说另一件事，两处不要写同一句话。

## 六、分布信息怎么写

抓取本身会产生"哪里有人做、哪里没人做"的分布，这比单纯推荐更有价值：

- 可以在结语或单独一节给出空白方向，例如某类关键词只搜到个位数项目、最高星标很低；**不要编造原因**，可以说"规则按国家走、责任重，愿意公开分享的人少"这类有依据的推断，并标明这是抓取结果。
- 给出"这对读者意味着什么"的一句话，例如"给编码助手用的技能已经卷起来了，日常办公那几类还空着"。

## 七、数据与实测口径

- 稿件末尾或元信息里写明抓取日期与来源（公开页面 + 各仓库 README + 自己的实测记录）。
- 星标、调用量、项目数、更新时间都是快照值；发布前建议回原始页面核对一次。
- 自己实测出来的数字（耗时、成本、成功率）要写清测试条件：什么任务、什么配置、跑了几次。
- 提醒读者：第三方技能是别人写好的指令，装之前先看内容、权限与数据三件事。
