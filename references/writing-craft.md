# 写作手感：把查到的资料写成有人愿意读完的稿子

这份文件管「同样的信息，怎么写成有人愿意读完、读完还能用上的样子」。第一节是基调，第二节是证据链，第三节是对标账号的落笔模板，第四节是落地要求，第五节起是机器能拦的硬约束；「简单易懂」的细则见 `readability.md`，结构与平行字段见 `editorial-rules.md`，红线见 `compliance.md`。

**不需要本机实测。** 文章的力量来自"信息真实 + 讲得清楚"，不是"我装过"。写法按下面的路子来。

## 一、基调：写你能证明的事，不写你猜的事

每句话都要能指回一个来源。三个层级，写的时候分清：

| 层级 | 是什么 | 怎么写 |
| --- | --- | --- |
| **官方口径** | README、官方文档、发布说明、定价页、官方公布的数字 | 照抄 + 标日期。数字不四舍五入，命令不改一个字 |
| **社区反馈** | issue、讨论区、HN / Reddit 帖子、别人的复现 | 写明"有人在 issue 里提到""作者在讨论区说"，不当作结论 |
| **我的判断** | 我认为它适合谁、我认为哪里会卡 | 用「我觉得」「如果你的活是……」引出，不要写成事实 |

三条不许：

- **不伪造实测。** 没跑过就不写"我装了""我跑了一遍""我测了六轮"。这类句子一旦被读者识破，整篇的可信度都没了。
- **不发明数字。** 星标、调用量、参数、价格、更新时间，全部来自当期抓取或官方页面；查不到就不写这个数字。
- **不把推断写成事实。** "大概是为了省成本"要写成"可以推测……"，并给出依据。

如果确实自己跑过（录了屏、截了图、有记录），可以写，但要在稿件元信息里标一行「自测」，并在 `素材/资料与出处.md` 里留记录。

## 二、证据链：每篇至少三处「查得到」

资料型文章一样有硬证据，只是换了一种。写完数一遍，不够三处就补：

| 证据类型 | 怎么写 | 例子 |
| --- | --- | --- |
| **官方原文** | 照抄关键句或命令，标明出处 | 「README 里写着一条命令装完：`npx skills add owner/repo`」 |
| **文档里的限制** | 官方自己写明的边界最可信 | 「文档明确写了单次上限 100 万 token」 |
| **社区反馈** | issue、讨论区的真实抱怨与复现 | 「issue 里有人反馈 Windows 下要先装 Node」 |
| **榜单 / 数据** | 排名、调用量、星标，都标日期 | 「OpenRouter 榜上排第 1，调用量 3.22T tokens（10-10 快照）」 |
| **版本与时间线** | 什么时候发的、多久没更新 | 「最近一次更新是 2026-10-02，之前停更了三个月」 |

凑不出三处，说明这个选题的资料太薄：要么换选题，要么缩小篇幅只写"它是什么"这一层。**不要用形容词填空。**

## 三、四种框架怎么落笔（含对标账号的模板）

对标账号有两个：公众号「阿川同学」（AI / 科技技术号，固定开场、`01/02` 分节、图文比约 1 张 / 120 字）
与公众号「逛逛GitHub」（开源项目推荐，日更、`01/02/03` 大号橙色编号、正文行高 2em、图文比 6.2 张 / 千字）。
完整的实测拆解见 `benchmark-guangguang-github.md`。

它俩的落笔习惯可以借，**但"我测了六轮"这类我们换成官方数据 + 文档 + 社区反馈**——
学结构、学语气、学图文节奏，不学第一人称实测。

**从「逛逛GitHub」提炼出的四条硬手感**（20 篇实测）：

1. **一句一段**。它的段落中位数是 **34 字**，97.6% 的段落 ≤80 字。每段一个意思，段间空行断开。
   这是它读起来不累的根本原因，比任何修辞都有效。我们的段落上限仍是 110 字，但**中位数应压到 80 字以下**
   （`qa.py` 会查）。
2. **标题 = 硬事实 + 人味**。前半截给可核对的数字或具体事实（Star 数、时间、平台、数量），
   后半截给人味评价或悬念，**用句号收尾**（显得平静，不像标题党）。
   前半截学，后半截里的夸张词（堪称一绝、玩疯了、太惊艳了）换成具体结果。
3. **不用口语垫词**。它 4.4 万字里「说白了」0 处、「其实」2 处，**几乎没有口头禅**。
   它的"人味"来自短段落 + 具体场景 + 少量自嘲。
   提醒：**去 AI 腔不等于加口头禅**——堆"说白了""讲真"只会换一种腔调。
4. **情绪不靠标点**。它全站破折号 **0 处**、感叹号 5 处。想要"有力"，把事实摆出来就够了。

| 框架 | 怎么分节 | 每节干什么 | 语气装置 |
| --- | --- | --- | --- |
| **项目手册** | `01` `02` `03` | 一节一个环节：装、跑通第一步、常用命令、踩坑 | 「说白了就是……」；「这一步最容易卡住」 |
| **科普解读** | `01` `02` `03` 或 `一、二、` | 一节一个问题：它解决什么、和已有方案差在哪、现在到哪一步了 | 先用生活化类比，再上正式说法 |
| **清单合集** | 按用途分组（3–5 组） | 一组一类活，每个项目一句"替你做什么" + 一条命令 | 「先挑最烦的那件活」 |
| **选型指南** | 先表后文 | 一张对比表定框架，再按典型场景给具体建议 | 「任务急选谁、要求稳选谁」 |

对标账号通用的四个部件，我们照用：

1. **固定开场三到五行**：期数 / 作者 / 首发 / 一句自我介绍 → 两句背景 → 一句"这篇讲什么" → 进入正文。
   （我们不放直播引导、加群引导、关注后领取——合规见 `compliance.md`。）
2. **开头就交出差异化钩子**：直接说"它让我好奇的地方是……"，不要留到结尾才揭晓。
3. **每节收一句人话**：把技术描述翻译成普通人的感受，例如"持续两个字才是它最有意思的地方"。
4. **结尾落到选择**：什么场景用它、什么场景别用、下一步做什么。

**不学的部分**：标题里的夸张词（王炸、炸裂、低调使用、绝了、堪称一绝、玩疯了、狠狠收藏）、
成串的感叹号、"绝对没有错"这类说法。
学结构、学证据、学语气，用词按我们自己的口径走（`qa.py` 会拦）。

## 四、让读者能用上：每篇都要给一个可执行的东西

读者读完要能做一件事，这篇才算有用。**每篇至少给一个能落地的东西**，四选一（多给不限）：

| 类型 | 长什么样 | 适用框架 |
| --- | --- | --- |
| 一条能照抄的命令 | 完整命令 + 前提条件，**用反引号包起来**（渲染成等宽小块，扫一眼就看见） | 项目手册、清单合集 |
| 一个最小示例 | 输入什么 → 得到什么 | 项目手册 |
| 一张对照表 | 固定维度横向比，**直接写 Markdown 表格**（不要做成图片，表里的数字要能复制核对） | 选型指南、科普解读 |
| 一条决策规则 | 「任务急选 A，要求稳选 B」 | 选型指南、清单合集 |

命令与参数在正文里一律用反引号包起来，转换器会渲染成**等宽 + 浅灰底**的小块。
这是"能落地"这条规则的视觉落点：读者滑的时候先看到这些小块，就知道这篇有能直接抄走的东西。

可执行的写法有固定四件套：**具体动作 + 前置条件 + 预期结果 + 出错怎么办**。

- 「在设置里调整一下」不算可执行；写「点右上角齿轮 → 高级 → 把并发改成 4」才算。
- 命令照抄官方，连参数一起；缺 Node、缺密钥、要账号，都要在这一句里说清。
- 说清"做完你会看到什么"（出现一个绿色的对勾、生成了一个 xxx 文件），读者才知道自己成功了。
- 给一个最常见的报错和它的处理办法，比加一段感慨有用得多。

三条让内容落地的做法：

1. **场景写到读者手上的活**：不写"提升效率"，写"周一要交的那份周报"。
2. **第一次用只做一件事**：最小路径三步以内，别一上来就把全部功能讲完。
3. **给判断标准**：什么情况用它、什么情况别用，让读者对号入座；只夸不用，读者反而做不了决定。

**落地四问**（写完自问）：

- 读者读完，具体能做哪一件事？
- 这件事他今天就能做吗？如果不能，缺的前置条件我写了吗？
- 做完他怎么知道成了？
- 卡住的时候，他能在文里找到下一步吗？

`qa.py` 会查"通篇有没有可照抄的东西"（命令、步骤、链接、表格），一个都没有就报警。

## 五、机器会拦的（`scripts/qa.py` 检查）

**硬禁用词**（出现即 FAIL，就地换成人话）：

赋能 · 抓手 · 闭环 · 生态位 · 全方位 · 一站式 · 在当今 · 随着…的发展 · 综上所述 · 总而言之 ·
众所周知 · 不难看出 · 值得注意的是 · 让我们 · 接下来 · 不可否认 · 显而易见 · 极大地 · 大大提升 ·
助力 · 打造生态 · 深度赋能

**慎用词**（全篇合计出现超过 2 次就报警）：

其实 · 非常 · 极其 · 深度 · 重磅 · 堪称 · 海量 · 强大 · 完美 · 极致 · 无与伦比

**标点**：

- 破折号「——」全篇 ≤8 处，且**同一个字段里最多 3 条**用「——」接续。
- 感叹号 ≤2 处。想要"有力"，用事实和数字，不用标点。
- 引号统一「」；正文与图注都不放 emoji。

违规词、极限词（"最""第一""100%"这类）与敏感话题见 `compliance.md`，`qa.py` 一起查。

## 六、句式黑名单

1. **三段排比**：「第一…第二…第三…」「首先…其次…最后…」——读者一眼看出是模板。
2. **「不是 A，而是 B」** 全篇最多一次。
3. **每段同一个收尾**：每条都以"适合…的人"结尾，读三条就腻。
4. **空话开头**：「随着 AI 的快速发展」「在这个信息爆炸的时代」——删掉不损失任何信息。
5. **名词化**：把"进行安装"写成"装"，把"实现效率提升"写成"快了 3 倍"。
6. **形容词堆叠**：连续两句只有评价没有事实，就把其中一句换成数字、命令或官方原话。
7. **无主语的客观体**：「可以看出该工具表现优异」——换成「文档给的数据是……，我查了它的更新记录，最近一次是 10-02」。
8. **术语轰炸**：一句话里两个以上没解释的英文词。改法见 `readability.md`。

## 七、写出人味的具体做法

- **抽象换具体**：不写"存在兼容性问题"，写"issue 里有人贴出报错：剪映 5.9 之后导出会卡在弹窗上"。
- **敢写短句**：4–10 字的短句独立成段用来换气，每节最多一两处。
- **敢有态度**：一句轻吐槽、一句自嘲都行，但不阴阳竞品、不下行业判决。
- **每个项目至少一个场景**：谁、在什么情况下会用到它。只有功能清单的条目说服力为零。
- **抄一手细节**：README 原话、官方给的数字、文档里明确写出的"做不到什么"。
- **写取舍**："什么人不用装"要写到读者能对号入座，比再夸一遍有用得多。
- **保留不确定**：拿不准的写"据官方文档""有人在讨论区提到"，不要替作者下结论。
- **数字要能对账**：正文里的星标、参数、价格，必须能在 `素材/资料与出处.md` 里找到出处。
- **把结论往前放**：先说什么，再解释为什么，最后才是细节。读者随时可能走。

## 八、把人留到结尾的结构

1. **前 100 字给答案**：这段写给谁看、读完能拿到什么、大概几分钟。别用行业大势铺垫。
2. **每节先给一句"这节看什么"**：先给结论或场景，再进条目。
3. **用桥句，不用悬念**：读者是滑着看的，"后面会讲到"会让人直接退出；直接说下一节是什么。
4. **每 2–3 段给一个可核对的东西**：数字、命令、截图、官方原话、出处。
   对标账号的做法是**每 2–3 段一张图**（6.2 张/千字）——图比数字更省读者的力气。
5. **长短句交替**：连续三段长度接近就拆一段——机器会拦，见 `qa.py` 的节奏检查。
6. **每节结尾给一句话的人话总结**，不要每节都收在"功能很强"上。
7. **结尾点名**：说清楚"先装哪个 / 先看哪个"，再补一句边界提醒；不要"让我们一起期待"这类空号召。
8. **段落压短**：目标中位数 **50–80 字**，一句话能讲完的就独立成段。
   段落一长，行高 2em 的透气感就被抵消了（版式见 `wechat-layout.md`）。

## 九、交稿前逐条自问

- 每句话都能指回一个来源吗？有没有我没查证就写下的数字或判断？
- 有没有写"我装了 / 我跑过"？如果没有真跑过，删掉或改成资料口径。
- 有没有哪一段换个主题也能用？删。
- 遮住项目名，读者还能说出它替谁干活吗？
- 术语第一次出现的时候，一个外行看得懂吗？
- 读者读完具体能做哪一件事？有没有一条能照抄的命令、步骤或对照表？
- 该说的前置条件（环境、密钥、账号）都写了吗？做完怎么判断成功？
- 前 100 字里，读者知道继续读能拿到什么吗？
- 有没有连续两句都在形容、没有事实？改掉一句。
- 限制与坑写了几处？一处都没有，读者会当成软文。
- 有没有为凑字数写的内容？删掉之后文章更好还是更差。
- 小标题连起来读，像要点还是像目录？

这份清单也是 `qa-checklist.md` 目视项的一部分：机器查得到的（禁用词、标点频次、段落节奏、句式重复、违规词、信息密度）由 `qa.py` 拦，查不到的（场景、桥句、易懂程度）靠这里和 `readability.md` 逐条过。
